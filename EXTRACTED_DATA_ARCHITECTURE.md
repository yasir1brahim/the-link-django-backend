# ExtractedData Architecture Overview

## Executive Summary

The ExtractedData model is a core data structure in The Link's Django project that manages extracted data from AI-generated logs and human-created highlights. It serves as a normalized, queryable representation of structured information extracted from PDF specifications.

---

## 1. Core Models

### 1.1 ExtractedData Model
**Location:** `/Users/averypawelek/the-link/the_link_django/apps/deliverables/models.py` (lines 465-560)

```python
class ExtractedData(BaseModel):
    """Individual row extracted from AI-generated logs or manually created via Apryse highlights"""
```

#### Foreign Keys
- `ai_generated_log` (ForeignKey → AiGeneratedLog): References parent AI log (null for human-created)
- `project` (ForeignKey → Project): The associated project
- `project_version` (ForeignKey → ProjectVersion): Version of the project
- `spec_section` (ForeignKey → SpecSection): Optional PDF section reference

#### Creation Metadata Fields
- `source` (CharField with choices): Either "AI" or "HUMAN"
  - Default: `ExtractionSource.AI`
  - Indicates whether item was AI-generated or human-created
- `created_by` (ForeignKey → User): User who created or triggered generation
  - SET_NULL on user deletion
  - Auto-populated from `ai_generated_log.created_by` if not set

#### Core Data Fields
- `spec_section_number` (CharField, max_length=256): e.g., "03 3000"
- `spec_section_name` (CharField, max_length=512): e.g., "Concrete"
- `paragraph_number` (CharField, optional): Reference within spec section
- `requirement_text` (TextField): The main content/requirement text
- `responsible_party` (CharField, optional, max_length=512): Party responsible for requirement

#### Type Classification Fields
- `extraction_type` (CharField, max_length=256):
  - For AI logs: `inspection_log`, `owner_deliverables_log`, `qa_planner`
  - For human-created: Base type selected by user (e.g., `submittal`)
- `item_type` (CharField, optional, max_length=256):
  - For QA Planner: Specific QA category
  - For human highlights: User-selected type
  - Can be null for simple extractions

#### Type-Specific Data
- `metadata` (JSONField, default=dict):
  - Type-specific data storage
  - Examples:
    - Inspection logs: `inspection_frequency`, `when_due`
    - Owner deliverables: `deliverable_type`, `when_due`
    - QA Planner: `when_due`
    - All: `raw_item` (original data)
  - Previously had separate fields (now consolidated)

#### PDF Integration
- `pdf_locations` (JSONField, optional):
  - PDF coordinate data for highlighting
  - Format: Array of location objects with `page` and coordinates

#### Metadata
- Database table: `deliverables_extracted_data`
- Ordering: `['spec_section_number', 'id']`
- Indexes:
  - `(project, project_version)` - For filtering by project
  - `(spec_section_number)` - For spec lookups
  - `(extraction_type, item_type)` - For type-based filtering
  - `(source)` - For AI vs HUMAN filtering
  - `(created_by)` - For user-created items

### 2.3 ExtractedDataCreateSerializer

Serializer for creating human-sourced ExtractedData:

```python
class ExtractedDataCreateSerializer(serializers.ModelSerializer):
    class Meta:
        model = ExtractedData
        fields = [
            'project', 'project_version', 'spec_section',
            'spec_section_number', 'spec_section_name',
            'extraction_type', 'item_type', 'paragraph_number',
            'requirement_text', 'responsible_party', 'metadata',
            'pdf_locations'
        ]

    def create(self, validated_data):
        """Set created_by and source from request context"""
        request = self.context.get('request')
        if request and request.user.is_authenticated:
            validated_data['created_by'] = request.user
        
        # Always HUMAN source for manual creation
        validated_data['source'] = ExtractionSource.HUMAN
        
        return super().create(validated_data)
```

```python
class ExtractedDataViewSet(viewsets.ModelViewSet):
    """ViewSet for ExtractedData CRUD operations"""
    permission_classes = [IsAuthenticated, ProjectAccessPermissions]
    filter_backends = [filters.SearchFilter, filters.OrderingFilter]
    
    # Search fields
    search_fields = [
        'spec_section_number', 'spec_section_name',
        'requirement_text'
    ]
    
    # Ordering fields
    ordering_fields = [
        'spec_section_number', 'created_at', 'updated_at',
        'extraction_type', 'source'
    ]
    ordering = ['spec_section_number', 'id']
```

#### Endpoints

**Standard CRUD:**
- `GET /api/projects/<project_id>/extracted-data/` - List (paginated)
- `POST /api/projects/<project_id>/extracted-data/` - Create (HUMAN source only)
- `GET /api/projects/<project_id>/extracted-data/<id>/` - Retrieve
- `PATCH /api/projects/<project_id>/extracted-data/<id>/` - Partial update
- `DELETE /api/projects/<project_id>/extracted-data/<id>/` - Delete

**Custom Actions:**
- `GET .../extracted-data/summary/` - Get extraction summary statistics
  - Returns total count, breakdown by source, breakdown by type
- `GET .../extracted-data/by_spec_section/` - Get extractions for a spec section
  - Query param: `spec_section_number`

#### Query Optimization
- **List action:** Uses `select_related('created_by', 'ai_generated_log')`
- **Retrieve/Update:** Uses `select_related('created_by', 'ai_generated_log', 'project', 'project_version', 'spec_section')`

## 6. Data Migration Patterns

### 6.1 Migration from AiGeneratedLog.log_data
**Location:** `/Users/averypawelek/the-link/the_link_django/apps/deliverables/migrations/0067_migrate_ai_log_data_to_extracted.py`

Migrates legacy data from `AiGeneratedLog.log_data` (JSON array) to individual `ExtractedData` records:

```python
# Text field mapping by log type
text_field_map = {
    'inspection_log': 'Inspection Type And Requirements',
    'owner_deliverables_log': 'Exact Requirement Text',
    'qa_planner': 'Requirement Text',
}
```

**Process:**
1. For each successful AiGeneratedLog with log_data
2. Iterate through items in log_data array
3. Create ExtractedData record with:
   - `ai_generated_log` → parent log
   - `extraction_type` → log_type
   - `source` = 'AI'
   - `created_by` → from ai_generated_log
   - `metadata` → type-specific fields

**Metadata Population by Type:**
- **inspection_log:** `inspection_frequency`, `when_due`
- **owner_deliverables_log:** `deliverable_type`, `when_due`
- **qa_planner:** `when_due`, `item_type`
- **All:** `raw_item` (original data), `original_text_key`

## 7. Data Flow & Use Cases

### 7.1 AI-Generated Extractions

```
1. User uploads PDF specification
   ↓
2. System processes PDF via AI pipeline
   ↓
3. AiGeneratedLog created with log_data (JSON array)
   ↓
4. Migration/Webhook creates ExtractedData records
   - source = AI
   - created_by = user who triggered generation
   - extraction_type = log type
   - metadata = type-specific fields
   ↓
5. ExtractedData items queryable via API
```

### 7.2 Human-Created Extractions (via Apryse Highlights)

```
1. User creates PDF highlight in Apryse viewer
   ↓
2. Frontend calls POST /extracted-data/ with:
   - spec_section_number
   - spec_section_name
   - extraction_type (user-selected)
   - item_type (optional user selection)
   - requirement_text (highlighted text)
   - pdf_locations (highlight coordinates)
   ↓
3. Serializer automatically sets:
   - source = HUMAN
   - created_by = authenticated user
   ↓
4. ExtractedData record created and stored
```

## 10. Key Design Patterns

### 1. Flexible Type Storage
- `extraction_type`: Fixed categorization (log type or base type)
- `item_type`: Optional subcategory (esp. for QA planner)
- `metadata`: Extensible storage for type-specific fields

### 2. Source Tracking
- `source` field distinguishes AI vs human-created
- `created_by` tracks originating user
- `ai_generated_log` FK for batch origin

### 3. PDF Integration
- `pdf_locations` stores raw highlight data
- `spec_section` provides section reference
- Integrates with PDFAnnotation for full highlight context

### 4. Query Optimization
- Strategic indexes on common filters
- select_related optimization in viewset
- Pagination for large result sets

### 5. Metadata Pattern
- Moved from individual fields to JSON object
- Backwards compatible via migration
- Supports type-specific field extensions

## 12. Current Limitations & Notes

1. **No explicit color field**: Color styling handled separately in PDFAnnotation
2. **metadata field limitations**: JSONField without schema validation
3. **No foreign key to PDFAnnotation**: Both track highlights independently
4. **item_type optional**: Some extractions may not need subcategorization
5. **Metadata structure inconsistent**: Different structure for different types
6. **No audit trail**: No history of changes to extracted data
7. **No user permissions**: All authenticated users can create/edit items from projects they can access
